Soft auth wall · context-aware bottom sheet

A bottom sheet that slides up over the current screen when a guest user taps a protected action (Book, Save permanently, Follow, Comment, Publish). Preserves scroll position and context — never replaces the current screen. The subhead is context-aware: it names the specific action and content so the user understands exactly what they're signing up for.

DD refs: DD-003, DD-016
SRS refs: IAM-FR-010, IAM-FR-011, IAM-FR-005 (promoted to M0)
Triggers: book · save · follow · comment · publish

Context-aware subhead is the whole point
Instead of a generic "Sign in to continue" subtitle, the sheet names the specific content the user was trying to act on. "We'll keep The complete Spiti guide saved for you" is meaningfully different from "Sign in to save this item." The user hasn't lost context — the sheet is reassuring them that whatever they were doing will carry through.
Preserves scroll position · never replaces the screen
The screen underneath is dimmed to 55% brightness but remains visible. On dismiss ("Not now"), the sheet slides down and the user is back exactly where they were — no page reload, no lost state. The backdrop dim is applied via CSS filter, not a full overlay, so the user sees their original context.
Primary CTA is coral · phone OTP is the default path
Coral "Continue with phone" is the primary action because phone OTP is the default auth method in India (IAM-FR-001). The Google/Apple buttons are secondary, below the primary, outlined not filled. This is opposite to the Western default where Google/Apple usually sit at the top.
IAM-FR-005 (Social login) promoted from [DEF] to [M0]
In SRS v1.1, Google/Apple login was deferred. DD-016 promotes it to M0 because the auth wall needs a secondary path — asking a guest to go through a full phone OTP flow just to save an item is too much friction. Google/Apple completes the sign-in in 2 taps if the user is already logged into the OS.
On successful sign-in, the original intent is performed automatically
If a guest tapped "Save" and then signed in, the save action executes as soon as the sign-in completes. The user doesn't have to tap Save again. This is critical — the whole point of a soft auth wall is zero friction loss.
SEO crawler bypass (BR-IAM-011)
The auth wall MUST NOT fire for search engine crawlers — Googlebot, Bingbot, etc. need to index the public content directly. The component checks the user-agent against an allow-list and simply does not mount the sheet for crawlers. Critical for the SEO wedge (DISC-FR-007).

Context prop schema · how the subhead is generated
{
  action: 'save' | 'book' | 'follow' | 'comment' | 'publish',
  contextTitle: 'The complete Spiti guide', // content title
  contextName: 'Riya Menon', // creator name for follow
  returnUrl: '/itinerary/spiti-guide', // scroll restoration
  returnAction: () => save(contentId) // re-execute on success
}
The calling component passes these props when it triggers the sheet. The sheet interpolates the subhead from a lookup table and queues the returnAction to fire on successful sign-in.
Content-safe interpolation (XSS prevention)
Because contextTitle comes from user-generated content (creator-published titles), the interpolation must escape HTML entities. A creator publishing "<script>alert('xss')</script>" as a title would otherwise break the sheet. Use React's default string interpolation (which escapes by default) or Flutter's Text widget — never dangerouslySetInnerHTML / RichText.parse on user input.
